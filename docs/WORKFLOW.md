# Evidence workflow

1. Outside this repository, obtain the official DISA XCCDF Benchmark and CKLB 1.0 JSON schema. Pin their provenance independently. Prepare an asset record using [v1 contract](../contracts/asset-record-v1.md) and a pre-scan whose **exact bytes** hash to `pre_scan_sha256`. The record is a handoff assertion, not a proof of baseline state.
2. Prepare a versioned master policy. Replace every placeholder in `stig_evidence/policy.example.json`. Generate tailoring with `python -m stig_evidence.cli tailor` and scan the exact host: fresh untailored pre and coverage with the policy base profile, tailored post with the generated profile. Retain the XML results. Pre < post <= coverage; all rules must appear in pre/coverage, all selected rules in post, and post statuses must agree with coverage. The pre scan may be up to 72 hours old; the other scans use the 24-hour default freshness limit.
3. Obtain ISSO approval in an external authorization process. Produce a JSON ledger with `schema: 1`, SHA-256 digests of the **exact** policy and benchmark files, and `approvals` entries whose `approval_id`, `rule_id`, `approver`, `disposition`, and `expires` match each exception. Sign the ledger bytes with an external private key using OpenSSL (`openssl dgst -sha256 -sign /private/isso.key -out /private/ledger.sig /private/ledger.json`). Establish the verification public key's owner out of band. Do not copy private keys into this repository.
4. Release with `python -m stig_evidence.cli cklb` (full syntax in [README](README.md)). `--asset` and all other release inputs are snapshotted once into a private temporary directory before the gate. The asset FQDN must equal `--host` exactly; its pre-scan hash is checked against the **snapshot**, not reopened source. The signed ledger, policy, tailoring, scans, chronology, coverage, pinned official schema, and target identity are checked before evidence publication. Supply an existing owner-owned `0700` evidence parent. Publication creates an unpredictable private staging directory there, writes through its held directory descriptor, then uses Linux `renameat2(RENAME_NOREPLACE)` to publish the complete bundle; existing names (including symlinks) are never overwritten. Parent and bundle identity are checked before returning the CKLB path. If a race or write fails, no success path is returned; a partial staging bundle or already-published bundle may remain for operator inspection, and is not automatically deleted.
5. Check `manifest.json`: it records hashes of every copied input, the CKLB, and `metadata.asset_sha256` binding the asset snapshot. Import the CKLB into STIG Viewer and independently review evidence, then obtain signed per-asset acceptance. The emitted `review_state` explicitly remains pending; CKLB statuses never automatically authorize remediation or close a finding.

Release is read-only with respect to inputs. The owner-only parent and random staging name block other users from replacing staging entries; inode checks detect replacements across the checked boundaries. A concurrent process with the **same UID** can still interfere between creation and the first identity check or after the final check, and no filesystem API can promise that a returned pathname stays stable indefinitely. Protect the parent and its ancestors operationally from same-UID mutation while releasing. It does not collect from a guest, attest a VM, prove a scan was executed on the named asset, authenticate the upstream lab handoff, or validate licensed media. Tests use synthetic XCCDF and ephemeral signing keys; a green suite is **not** real-world STIG compliance or acceptance.
